PART 1 SLIDE 2 OF 12 • PROBLEM IDENTIFICATION

PR Approver Configuration: Background & Root Causes

Understanding why PR approver errors occur and identifying them using T-Code ZR190.

ZR190

🔍 Background & Why Errors Occur

The PR (Purchase Requisition) approver change process is initiated when an error occurs in the document due to an issue with the assigned approver. This typically happens for three primary reasons:

  • 1
    No approver maintained in the system:
    No active user or approver has been assigned or maintained in the organizational structure for the specified release position.
  • 2
    Expired approver validity:
    The assigned approver's validity period has expired, or the employee has resigned/transferred, leaving the position unfulfilled.
  • 3
    Change in approval workflow:
    The original approver is no longer responsible due to organizational realignment or departmental changes. (Applicable when replacement is needed).
📌
Objective: The PR approver must be updated to ensure the document is routed to the designated approver so that the approval workflow can proceed seamlessly without blockage.

PART 1 SLIDE 5 OF 12 • CONFIGURATION STEP 3 DEV 510

Release the Transport Request (TR)

Using SE10 Transport Organizer with strict hierarchical release order.

SE10

📦 TR Release Rules & Procedure

  • 1
    Log in to DEV 510:
    Execute transaction code SE10 to open the Transport Organizer.
  • 2
    Display Modifiable Requests:
    Check Customizing Requests & Modifiable, then click Display.
  • 3
    CRITICAL RULE — Release Child Task First:
    Highlight the sub-task (second TR) first (e.g. DEVK9A05F6 Customizing Task). Click Release Directly (the red truck icon 🚚).
  • 4
    Release Parent Request Second:
    After the child task completes release, highlight the main TR (first TR) (e.g. DEVK9A05F5) and click Release Directly (truck icon 🚚).
⚠️
HIERARCHY RULE: You cannot release the parent TR while its sub-task is still open/modifiable! Always release the sub-task first. Once both are released, the TR is ready for QAS import.

Claim Tag: Ticket Analysis & SLG1 Application Log

Investigating "Unable to receive claim notification" tickets via SLG1 Unix logs.

SLG1

📨 Incident Analysis & SLG1 Log Investigation

Sample Ticket: User reports "Unable to receive claim notification due to incorrect email address maintained in SAP" (e.g. ticket KP-57140).

💡
Mandatory First Action: Always ask the user for the Claim tag number or Document number if not specified in the ticket!

Checking Logs via SLG1:

  • 1
    Object: Input ZUNNIXMAIL
  • 2
    Subobject: Select based on document type:
    • GIMOD: Goods Issue Notification
    • GIREV: GI Reversal Notification
    • GRMOD: Goods Receipt Notification
    • GRREV: GR Reversal Notification
    • MRMOD: Material Requisition Notification
    • ZY28: ZY28 Unix Sending Log
  • 3
    External ID Formatting Rules:
    • For MRMOD: 4 leading zeroes + MR number + asterisk: 0000123456*
    • For GRMOD, GIMOD, etc.: Document number + asterisk: 500123456*
  • 4
    Time Restriction: Enter the date and time when the claim tag was dispatched, then Execute.

PART 2 SLIDE 10 OF 12 • REPROCESSING & FALLBACK

Resending the Claim Tag: ZR65A & ZR54

Reprocessing via Monitoring Report with fallback handling for unlisted documents.

ZR65A ZR54

📤 Standard Procedure via ZR65A

  • 1
    Execute ZR65A:
    Open transaction code ZR65A (Claim Tag Monitoring Report).
  • 2
    Enter Document Number:
    Input the target document number in the Document Number parameter field.
  • 3
    Ensure Selections Checked:
    Ensure checkboxes for Ariba MR, SAP ECC MR, Ariba PO, and SAP ECC PO are enabled as needed. Click Execute (F8).
  • 4
    Verify Recipient Details:
    Highlight the specific line item. Verify recipient name and email address to ensure proper delivery destination.
  • 5
    Click Reprocess:
    Click the Reprocess button on the toolbar to re-send the notification.
⚠️
FALLBACK PROCEDURE (ZR54): If the claim tag does not appear in ZR65A, open ZR54. Enter Reference Number or Document Number + Employee ID. If found, resend from there.
🛑
EXPIRED CLAIM TAG: If the claim tag cannot be found in either ZR65A or ZR54, it means the claim tag has already expired. The user must submit a brand new request.
